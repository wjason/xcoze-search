# Keyless, DeepSeek and Smart: live task comparison

[简体中文](2026-11-03.md) | **English**

Tested 2026-11-03 on local macOS/Python 3.10 with an existing DeepSeek key. Credentials and saved preferences were unchanged. Baseline: `e758498` (v0.4.1). Optimized runs used the v0.5.0 routing changes on that base; recorded runtime version was still 0.4.1 at execution time. [Sanitized observations](2026-11-03.data.json) contain timings, URLs, receipts and manual reviews, without keys or copied excerpts.

## Findings and changes

Paid search was faster in this sample, but did not consistently retrieve better evidence. The old Smart stopped at any nonempty response, so it could not repair missing primary sources. Native GitHub/HN routing helped, particularly for dated HN discussions.

- General keyless search now starts with Exa hosted MCP; Bing RSS and DuckDuckGo remain fallbacks. Bing returned unrelated nonempty results for three tasks in the baseline.
- Quality reference/current tasks may consult a complementary source within the existing two-source cap: DeepSeek then keyless Exa on this machine. General tasks, explicit source selection and successful platform routes still stop as specified. Free/balanced do not force two-source search.
- Experimental RSS/HTML responses with zero recognizable topic-token overlap produce `irrelevant_results` and may fall back. This conservative signal does not assess facts, completeness or Chinese semantics; queries with fewer than two informative Latin tokens skip it.
- The Agent derives internal `--intent reference|current` from the original question, without asking users to choose a mode. Current prices, rules, versions and conflicting snippets require current primary-page reading.

This is a small development study, not a general accuracy estimate or a permanent provider ranking.

## Method and limits

Six tasks and review criteria were fixed before the baseline. We ran the original implementation, a keyless-order-only revision, then the intent/complement revision. After freezing routing, we added two Chinese holdout tasks. Modes ran sequentially per task with rotated execution order: at most five results per source, zero retries, 15-second request timeouts, a 31-second scheduling budget and two-source auto cap. The diagnostic time budget differs from the released 45-second default.

Free excludes keyed adapters; DeepSeek pins one source; Smart uses the actual configured DeepSeek account and public routes. HN native search uses UTC calendar filters; explicit DeepSeek uses documented `after:/before:` operators plus site scope, with the exact query retained. This compares task-appropriate adapters, not identical wire payloads.

Timing covers in-process retrieval, excluding process startup, answer generation and separate verification reads. There is one observation per task per run, no confidence interval or load test. Remote caches, indexes and ordering can affect results. Later rounds were substantially faster; code changes alone cannot explain that difference.

Manual review separates relevance, primary-source discovery, support for the requested detail, freshness and remaining reading needs. HTTP success, nonempty output or an official-domain URL does not establish correctness. Private review excerpts were capped at 1800 characters per result; truncated material was not assumed read. Public data retains URLs and review notes only.

## Freshness: two Chinese holdouts

Routing was frozen before these runs; their outcomes did not change source order.

- **SQLite WAL concurrent writers/readers:** all modes found related material; keyless/Smart added the canonical WAL page alongside BEGIN CONCURRENT branch docs. Standard WAL permits readers alongside one writer; the optional branch must not be presented as default behavior. Review [canonical WAL](https://www.sqlite.org/wal.html) and [branch docs](https://sqlite.org/src/doc/begin-concurrent/doc/begin_concurrent.md) separately.
- **Current private-repository GitHub Actions billing:** DeepSeek official-domain indexed excerpts retained historic included-minute wording. Keyless/Smart surfaced current included-compute-usage wording, confirmed by reading the current official page. Official URLs can carry stale indexed excerpts. Read [current billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions) and [included usage](https://docs.github.com/en/billing/reference/product-usage-included); do not vote across conflicting sources.

HN provided structured publication dates that met the interval. Many other dates were null; unknown does not mean stale or fresh. Current rules/versions were checked by reading pages. General index lag was not measured.

For two holdouts, keyless/DeepSeek/Smart medians were 1.09/0.56/1.61 seconds, HTTP counts 2/2/4, and estimated search cost USD 0/0.00150/0.00150.

Final Smart added four keyless requests while retaining four billable DeepSeek successes. Platform routes avoided paid calls; current/reference tasks added evidence and waiting time. This is not a universal savings claim.

Estimates use the dated [official Search/Fetch price](https://api-docs.deepseek.com/guides/search/#billing): USD 0.75 per 1000 successful requests, excluding empty results, failures and timeouts. Billable search success was counted on raw nonempty responses before site filtering, not displayed rows. No invoice amount was returned. Model tokens, subscriptions and local compute costs remain unknown/null. Keyless means no user-keyed API charge from this tool, not zero total cost.

All four runs: 60 mode cells, 66 search HTTP attempts, 31 nonempty DeepSeek successes, known search cost estimate USD 0.02325. Separate verification read five known pages in six HTTP calls (five Jina, one GitHub 403), with no keyed Fetch. Python downloads was truncated at 24000 characters, but the needed version/date was in the read portion. These reads are excluded from retrieval timing and do not establish full-page completeness.
